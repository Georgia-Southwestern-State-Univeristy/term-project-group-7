# Week 15 Final Sprint Goal + Closing Backlog

## Sprint Goal
Complete final-readiness closure work by rehearsing the exact presentation demo path, validating both successful and failure-case runtime behavior, bringing the hand-off materials to near-final quality, and making team accountability visible through evidence-backed documentation.

## Sprint Window
- Week: 15
- Sprint type: Final readiness / closure sprint

## Why This Sprint Exists
This sprint is not a feature-growth sprint. It exists to reduce final presentation risk, verify the real runtime path a reviewer will follow, document what happens when the system works and when it fails, and make the project understandable to someone outside the team.

## Committed Items

### 1. Run and document the final QA pass
- **Owner:** Victor Grey
- **Acceptance Criteria:**
  - `docs/final/week15-qa.md` includes at least 10 specific checks
  - the exact final demo path is documented step by step
  - the QA pass includes startup, runtime, core workflow, and error-handling verification
  - rehearsal notes state what succeeded, what was confusing, what broke, and what was fixed or mitigated
  - final high-priority PRs are linked

### 2. Rehearse the final demo path end-to-end
- **Owner:** Victor Grey
- **Acceptance Criteria:**
  - the team has a defined live demo sequence
  - the demo sequence includes both successful workflow behavior and at least one failure-path explanation
  - the demo path is realistic for the final presentation and does not rely on unverified steps
  - runtime dependencies needed for the demo are identified clearly

### 3. Finalize the presentation plan and speaking roles
- **Owner:** David Hugee-James
- **Acceptance Criteria:**
  - `docs/final/week15-presentation-plan.md` defines a 12-15 minute structure
  - each team member has a clear speaking role
  - a demo driver and backup support person are assigned
  - a backup plan exists if the live demo partially fails
  - presentation notes or outline are included directly in the file

### 4. Bring the hand-off document to near-final quality
- **Owner:** David Hugee-James
- **Acceptance Criteria:**
  - `docs/handoff/hand-off-draft.md` is updated into a near-final reviewer-facing document
  - it includes system overview, architecture snapshot, stack rationale, setup summary, known issues, constraints, next steps, and user/admin guidance references
  - it reflects the current Windows-first C++ + GUI + HTTP + SQLite project honestly
  - no major section is left as an empty placeholder

### 5. Record Week 15 hand-off completion status
- **Owner:** David Hugee-James
- **Acceptance Criteria:**
  - `docs/final/week15-handoff-status.md` identifies what is complete
  - any remaining cleanup is described honestly as minor cleanup, not hidden
  - the status doc clearly states what still needs final evidence-link replacement if applicable

### 6. Make individual contributions visible and concrete
- **Owner:** Victor Grey
- **Acceptance Criteria:**
  - `docs/final/week15-contributions.md` lists each member’s role
  - each member’s major contributions since Beta are stated concretely
  - each member has evidence references such as PRs, docs, or reviewable repo work
  - each member’s final presentation responsibility is defined

### 7. Confirm peer evaluation completion
- **Owner:** Victor Grey
- **Acceptance Criteria:**
  - the team roster is listed
  - completion is confirmed for all team members
  - a completion date is recorded
  - no private peer-evaluation responses are included in the repo

### 8. Resolve final documentation drift and reviewer confusion
- **Owner:** Ridhwaan Jimoh
- **Acceptance Criteria:**
  - final documentation no longer conflicts with the current README or runtime behavior
  - docs consistently describe the Windows GUI, local HTTP API, SQLite-backed question data, and runtime asset expectations honestly
  - obvious placeholder wording is removed or replaced where possible

## Closing Backlog Notes
This backlog is intentionally closure-focused. Week 15 work is about final verification, demo confidence, documentation integrity, and reviewer clarity. If this backlog still reads like future feature planning, the team is off target.
